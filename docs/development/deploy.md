# Deploying ViStud to vistud.app

How ViStud reaches production at **https://vistud.app** (decisions 2 and 7 of [docs/specs/mcp-connections-plan.md](../specs/mcp-connections-plan.md), section 5). The MCP server is `https://vistud.app/mcp`. That address never changes after launch: a change signs every connected AI app out.

`.app` is an HTTPS-only domain (HSTS preload): the site needs a certificate from the first request. Abel runs releases; nobody pastes secrets into a chat, a ticket or a commit.

## The server

A VPS with 2 vCPU and 4 GB is enough for one learner.

| Piece | Setting |
|---|---|
| OS packages | nginx, **PHP 8.4** FPM (8.4.1 or later; `vendor/composer/platform_check.php` refuses older) with `pdo_mysql`, `mbstring`, `intl`, `sodium`, `zip`, `gd`; MySQL 8.4; Composer 2; Node 22 for the build; LibreOffice for Office previews; supervisor; certbot |
| DNS | An `A` record for `vistud.app` to the VPS. If Cloudflare is used, `/mcp`, `/oauth/*` and `/.well-known/*` must be **DNS-only**: the proxy cuts calls at 125 s and has blocked Claude's token exchange (laravel/mcp issue #210) |
| TLS | Let's Encrypt (`certbot --nginx -d vistud.app`), renewed automatically |
| Redirects | `http://` to `https://` only, and no redirect to another host: Claude drops the `Authorization` header across hosts |
| Database users | Two MySQL users, as in [setup.md](setup.md#database-users): the schema owner for migrations, the restricted runtime user for the app |

### nginx

The usual Laravel site, plus for `/mcp` the time Claude allows a call (240 s):

```nginx
location = /mcp {
    try_files $uri /index.php?$query_string;
}
location ~ \.php$ {
    fastcgi_read_timeout 250s;   # /mcp calls; McpPrincipal sets PHP's limit to 230 s
    # ... the usual fastcgi_pass and params
}
```

### .env on the server

Copied privately, never committed. The values that differ from local:

```dotenv
APP_ENV=production
APP_DEBUG=false
APP_URL=https://vistud.app
APP_KEY=        # the SAME key as the local install (see the go-live migration)
LOG_LEVEL=warning
QUEUE_CONNECTION=database
SESSION_SECURE_COOKIE=true
MCP_ENABLED=true
TUNNEL=0
```

### Processes

- **Queue worker** (supervisor): `php artisan queue:work --tries=3 --max-time=3600`. Required: without it big PDFs are never read (`ExtractFileText`), previews are never made, and the reader's jobs never run.
- **Scheduler** (cron, every minute): `* * * * * cd /var/www/vistud && php artisan schedule:run >> /dev/null 2>&1`. It runs session settling every ten minutes, `passport:purge` hourly, and the nightly prune jobs (`vistud:mcp:prune`, `vistud:db:orphans`, `vistud:engine:prune-threads`, the trash).
- **Passport keys**: made on the server with `php artisan passport:keys`, mode 0600, never copied from a laptop and never in git.

## Go-live migration (once)

### Learner keys (S1): required before reopening the app

The application now has a separate `mysql_keys` connection and `mysql_keys_owner`
schema-owner connection. Create its database and grant runtime CRUD / owner DDL
privileges first; the exact local SQL is in [the S1 handoff](../handoff/second-learner-S1.md).
Use production users on the server. Keep key-database backups separate from data backups.

Inject `VISTUD_MASTER_KEY` into the environment of PHP-FPM, the scheduler, and every
worker: `base64:` followed by the base64 encoding of 32 securely generated bytes.
Generate and store it privately; never send it through chat or a command argument.
There is no fallback to `APP_KEY`. With `config:cache`, Laravel does not load `.env`,
so the process environment must supply the master secret. Do not put it in cached configuration.
Set `DB_KEYS_DATABASE` and any `DB_KEYS_*` connection overrides before caching configuration.

Only after Abel approves and a verified backup is available:

1. Put the app down, stop queue workers, and pause scheduled commands that create learners.
2. Run `php artisan migrate --database=mysql_keys_owner --path=database/key-migrations --force`.
3. Run `php artisan migrate --database=mysql_owner --force`.
4. Run `php artisan vistud:keys:provision --dry-run`, then `php artisan vistud:keys:provision`.
   **This gives Abel's existing learner its key. Do not omit it or reopen first:** MCP checks it immediately.
5. Resolve every missing/unreadable-key error; never generate a replacement for a previously provisioned learner.
6. Verify a key-backed round trip and `php artisan vistud:gate:second-learner` (still closed after S1).
7. If this release includes S2a or S2b, complete the text conversion procedure below before restarting anything.
   Otherwise restart workers with the environment above, resume the scheduler and reopen the app.

Never run `migrate:fresh` on either real database. Reverting the key migration deletes
keys and makes encrypted content unreadable; its `down()` exists for synthetic tests,
not for a live rollback. Restore a matching key backup instead.

Master rotation and recovery are in [operations.md](operations.md).

### Core personal text (S2a): offline conversion before reopening

This procedure now covers **S2a and S2b**. The default backfill selects both;
`--phase=S2a` or `--phase=S2b` selects only that part for a staged release or
rollback. If neither has been deployed, convert and verify both before reopening.
Do not run these steps on Abel's local database as a development check.

Abel runs these steps; they have not been run on his local database by the builder.
S1 key migrations and provisioning (including Abel's learner) must be complete.
Take and verify matching content/key backups and retain the master key privately.
Stop workers and the scheduler, then put the app in maintenance. Do not run old
workers alongside the new code: legacy rows are deliberately unreadable at runtime.

1. `php artisan migrate --database=mysql_owner --force` (both parts widen content columns).
2. `php artisan vistud:encrypt:backfill --dry-run`. Resolve every blocker first.
3. `php artisan vistud:encrypt:backfill --backup-confirmed`. A stopped command is
   resumed by repeating it; committed rows are verified and skipped.
4. `php artisan vistud:encrypt:backfill --verify`. It must exit successfully with
   zero blocked rows. Save its count-only report, never student text.
5. With the production database cache selected, run
   `php artisan vistud:encrypt:clear-text-caches --dry-run`, then
   `php artisan vistud:encrypt:clear-text-caches`. This deletes ChooseTopics and
   Troubles entries (including stale entries for deleted folders), without
   converting them. They refill encrypted. No global cache flush is needed.
6. Check opening/saving an existing note, note search, tutor history, a class
   transcript and an MCP read as Abel. Check a raw scratch row is ciphertext.
7. Restart workers, resume the scheduler, and reopen for Abel only.

The [manifest](../../app/Platform/Database/ContentColumns.php) separates both parts.
S3 still has files to convert; the second-learner gate stays closed
until **both S2a and S2b**, files, validation and the later admission checks pass.
The ordinary release procedure below must include these steps for either text release.

Rollback is also offline and needs a verified backup and readable learner keys:
run `php artisan vistud:encrypt:backfill --decrypt --backup-confirmed`, then roll
back both text migrations as the owner, and deploy the application preceding S2a.
To roll back **only S2b** to the approved S2a release, use
`php artisan vistud:encrypt:backfill --phase=S2b --decrypt --backup-confirmed`,
then `php artisan migrate:rollback --database=mysql_owner --step=1 --force`
only after checking S2b is the latest migration, then deploy the S2a code. S2a
rows stay encrypted. Stay in maintenance until code and schema match.
The migration refuses encrypted rows or values that would not fit the original
types. Never shrink ciphertext, recreate keys, or restore plaintext to a running
application. If conversion or DDL fails, keep maintenance on and resolve it or
restore matching backups; do not blindly use the generic release rollback.

Abel's study history is in the local MySQL and `storage/`. 2FA secrets, recovery codes and his own OpenRouter key are encrypted with `APP_KEY`, so the server must use the same key.

1. Locally: `.tools\backup-database.ps1`, and copy `storage/app` (the files, previews and texts).
2. On the server: restore the database dump and the files; put the local `APP_KEY` in the server's `.env`.
3. `php artisan migrate --database=mysql_owner --pretend`, read it, then `composer migrate`.
4. `php artisan passport:keys`, `php artisan config:cache`, `php artisan route:cache`, `php artisan view:cache`.
5. Check before cut-over: signing in with 2FA works; Settings › AI › the key's "test" passes; `curl -i -X POST https://vistud.app/mcp` answers **401** with a `WWW-Authenticate` header naming `https://vistud.app/.well-known/oauth-protected-resource/mcp`.
6. From then on, study on production only. The local copy is for development, with seeded or synthetic data.

### Private files (S3a): preparation only

S3a changes new uploads, note images and derived previews to the
[binary file format](../architecture/private-file-format.md). It deliberately
cannot read legacy plaintext. **Do not deploy/reopen this intermediate code on
Abel's existing files.** S3b must first deliver and validate the combined offline
file conversion, resume and rollback procedure. Its inventory must cover both
halves, including old preview locations and upload/digest fingerprints; see
[the S3a handoff](../handoff/second-learner-S3a.md). No file conversion command
exists in S3a, and no local deployment has been performed.

Before the later combined release, configure private source and disposable
derived disks, and configure memory-backed processing/upload/request temp paths
for FPM, CLI workers, the scheduler and nginx as described in
[operations.md](operations.md#private-file-storage-and-temporary-bytes-s3a).
PHP must have OpenSSL with AES-256-GCM. Keep source files/note images in matching
content/key backups; exclude derived files and all processing/upload temps.
Do not use the generic migration rollback below for a partially converted file
store. Stop writers and use S3b's verified recovery procedure instead.

### Private files (S3b): offline conversion

S3b completes the file converter required by S3a. Abel runs these steps later;
the builder has not run them on his database or files. Complete S1 key setup
(including Abel's key) and both S2 text conversions first. Configure private
source/derived disks and production RAM-backed temp paths as above. Keep matching
verified database/canonical-file/receipt/key backups and private master recovery.

1. Enter maintenance, stop workers, stop the scheduler and every upload writer.
   Never run old and new file writers together. Keep maintenance through checks.
2. `php artisan vistud:encrypt:files --dry-run`. Reconcile missing/orphan objects,
   conflicting copies, missing keys and old diagnostics against the backup.
   Save only the count report. Read the S3b handoff's legacy-header limitation.
3. `php artisan vistud:encrypt:files --backup-confirmed`. Repeat if interrupted.
   If the dry run found old disposable processing/upload temps, review/archive
   needed artifacts first, then add `--purge-temp-confirmed`. Saved Markdown is
   imported or blocked, never silently discarded by that flag.
4. `php artisan vistud:encrypt:files --verify`. Require unrestricted success with
   zero blockers. A learner-filtered or limited run is not a full release check.
5. As Abel, check file/image download, Office preview, extracted text, recording
   upload/recovery and seeking, and transcription. Restart the workers with the
   configured private temp environment, resume the scheduler and reopen for
   Abel only. The second-learner gate remains closed pending later phases.

Rollback stays offline: stop all writers, take/verify matching backups and run
`php artisan vistud:encrypt:files --decrypt --backup-confirmed`, repeating until
successful. Previews return to the source disk and hashes become original SHA;
old diagnostic Markdown is preserved at its learner-owned path. Deploy the
approved S2b code (before S3a), keeping S2 text encrypted and its schema in place.
Check plaintext file reads there before restarting. Do not deploy S3a alone over
decrypted files. If a source cannot verify, preserve it and restore matching
backups with Abel; do not delete keys, discard sources or improvise partial
schema/data rollback. See [the S3b handoff](../handoff/second-learner-S3b.md).

## A release

Run on the server, as the deploy user:

```bash
cd /var/www/vistud
php artisan down --retry=30
mysqldump ... > ~/backups/vistud-$(date +%F-%H%M).sql   # or the backup script
git fetch origin && git merge --ff-only origin/claude/persistent-study-context-zsilo6
composer install --no-dev --optimize-autoloader
npm ci && npm run build
composer migrate
php artisan config:cache && php artisan route:cache && php artisan view:cache
php artisan queue:restart
php artisan up
```

If a migration fails: `php artisan migrate:rollback --database=mysql_owner --step=1`, check out the previous commit, repeat from `composer install`.

## After the first release: connect the apps

- **claude.ai**: Customize › Connectors › Add custom connector, URL `https://vistud.app/mcp`. Sign in to ViStud, approve on the consent page. It then shows on the phone too.
- **ChatGPT** (Plus): Plugins › + › Add custom MCP server, the same URL. First check that the plan offers it at all (M6.2, ChatGPT step 1).
- **Antigravity CLI** (Google's test client): `serverUrl: "https://vistud.app/mcp"` in `~/.gemini/config/mcp_config.json`.

Gemini's redirect hosts are not in `config/mcp.php` yet: the first refused registration names them (plan §3.2).

## Restore drill (monthly)

Use the complete [S4b restore procedure](operations.md#every-restore-replay-before-any-access) monthly in an isolated scratch installation. Fetch the latest independent ledger/head, restore content and keys separately, replay before any access, verify erased and unrelated learners, then run `vistud:doctor`. Record the drill privately; never test a restore over Abel's local installation.

## Account erasure and independent restore protection (S4)

Before enabling erasure, provision and initialise S4b's independent ledger as
[operations.md](operations.md#independent-durable-ledger-setup-first-deployment-only) describes; import S4a history and verify the off-site checkpoint. See [S4a handoff](../handoff/second-learner-S4a.md) for the inventory,
retry procedure and privileged audit exception. Abel runs setup; no local account
or file deletion is part of development validation.

Apply the new main migration as `mysql_owner` after verified S2/S3 conversion.
Keep the database worker (job timeout 360 s, retry_after 420 s) and minute
scheduler running; due unfinished erasures are requeued every ten minutes.
The three-hour minimum grace must exceed every request, job and temporary-file
expiry plus janitor interval. Enforce FPM `request_terminate_timeout = 1800s` and
`request_terminate_timeout_track_finished = yes` so after-response work is bounded.
Use supervisor wall-clock termination for stuck CLI workers and subprocesses;
PHP timers alone exclude blocked I/O on Linux. Keep hourly temp pruning and S3's
memory-backed production temporary paths. Longer workloads require a longer grace.

The runtime may insert/read requests but cannot mark completion; only the
privileged worker updates progress and inserts the content-free ledger. Never
roll back nonempty erasure tables or restore an old ledger over the latest one.
Use the approved S4b retention and restore procedures in operations.md. Missing
independent ledger storage/key/checkpoint blocks erasure and restore replay; no
new database schema is required beyond S4a. Every restore, including keys/files
only, must replay the latest independent intent before reopening. Never place
the ledger key in config cache or bundle key backups into 35-day data backups.
